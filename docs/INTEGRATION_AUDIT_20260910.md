Нельзя использовать прежний зелёный отчёт 0.1 как свидетельство прохождения текущего main.

## Подтверждённые незакрытые замечания

### I1. TUI не подключён к штатному CLI

В main существуют monik/tui.py, client.py и словарь labels.ru.json, но cli.py не регистрирует подкоманду tui. Наличие модуля ещё не даёт устанавливаемой команды. Для завершения интеграции требуется совместная проверка CLI, установленного пакета, настоящего HTTP и PTY, включая выход и восстановление терминала.

### I2. Некорректные типы полей лимита сохраняются в проекции

Синтетический primary с used_percent={}, window_minutes=[] и resets_at="bad" возвращает те же значения. valid=false и remaining_percent=null корректно запрещают считать процент достоверным, однако сами некорректные поля продолжают доходить до клиентов. Необходимы отдельные проверки скалярных типов и отображения неизвестных значений.

### I3. Поздний конфликт меняет ранний event-time срез

Воспроизведён пример: исходный ответ имеет время события 100, поступает в 200 и содержит total=110. Конфликтная доставка того же ответа имеет то же время события, но поступает в 400. При T=300 event-view уже исключает измерение и возвращает null, тогда как knowledge-view возвращает 110. До изменения поведения нужно явно согласовать семантику: является ли event-view реконструкцией со всеми известными позднее исправлениями или должен ограничивать также время обнаружения конфликта. Сейчас нельзя обещать одинаковое отсутствие позднего влияния для обоих видов истории.

### I4. Структурная модель остаётся в settings.data

model={"unexpected":true} превращается в null в скалярном поле события, но объект остаётся в data.model. Текстовый интерфейс и браузер получают неодинаково нормализованные представления одного поля. Значения model/effort/tier должны иметь явный контракт типов; реальные строки протокола переводить не следует.

### I5. Обзор не является единой read-транзакцией

Каждый Store.connect() создаёт отдельное соединение; вложенные чтения не переиспользуют snapshot. Отдельный запрос usage согласован внутри себя, но карточки, настройки и конечный cursor всего overview могут относиться к разным моментам при параллельной записи. Это требует отдельного теста на согласованность, а не только арифметической сверки totals.

## Что не нужно переделывать заново

Пакет monik, конфигурация и SQLite-схема v1 уже существуют. Есть отдельный write-lock, приватные metadata-копии DB/WAL, источник происхождения событий и ограниченные курсоры. Нет необходимости начинать ещё одну параллельную реализацию observatory ради интеграции интерфейсов.

Исправление согласованной очистки структурных данных и поискового текста уже присутствует в этом main. Оно не делает старые базы и резервные копии очищенными задним числом и не является гарантией распознавания любого секрета.

## Воспроизведение без рабочих источников

Из отдельного клона/экспорта репозитория с установленными тестовыми зависимостями:

```bash
python -m unittest discover -s tests -p 'test_*.py' -v
python tests/fixture_validator.py tests
python tests/wire_acceptance.py --output /tmp/monik-wire.json
```

Тесты создают собственные временные источники. Не воспроизводите повреждение, усечение и заполнение диска на настоящих rollout Codex. Для установки и испытания на владельческом хосте нужны отдельные проверки путей, Landlock, отсутствия влияния на TUI, TLS и телефона.
